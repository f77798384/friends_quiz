# 朋友出題大會 Friends Quiz

朋友互相出題、作答、批改與比較成績的多人聚會測驗網站。使用手機或電腦的瀏覽器就能遊玩，無須另外安裝 App。

> **版本說明：** 本 README 整合截至 **v4.5.5（2026-10-30）** 的功能與歷次修正。這是供朋友私人遊玩的測試原型，非經過正式資安稽核的公開服務。

## 主要功能

| 類別 | 功能 |
| --- | --- |
| 房間 | 建立房間、使用代碼與暱稱／PIN 加入、顯示成員 |
| 主持人 | 在大廳剔除非主持人、鎖定題庫、在允許的階段解鎖、公布答案 |
| 出題 | 每位玩家最多 10 題、四種題型、編輯／刪除、預覽題目 |
| 圖片 | 題幹附圖；選擇題的 A／B／C／D 選項各自附圖；可僅有圖片而無文字 |
| 配分 | 預設每題 10 分、每位出題者 10 題共 100 分，第 10 題自動補足；阻止不合法配分 |
| 作答 | 僅需回答**其他人**出的題目，不回答自己的題目；完成後交卷 |
| 評分 | 選擇、是非、填空自動比對；簡答題由**原出題者**人工評分並顯示作答者暱稱 |
| 閱卷 | 公布答案後可依「作答者」或「出題者」查看作答成果 |
| 排行榜 | 排除本人題目的總榜、依出題者切換比較「誰最了解誰」 |
| 狀態恢復 | 分頁專屬 `sessionStorage`，重新整理後嘗試回到原房間；主動離開時清除 |

## 遊戲規則與完整流程

1. **主持人建立房間**：輸入暱稱與 PIN，取得房間代碼。
2. **朋友加入房間**：使用房間代碼、暱稱與 PIN 加入。每人使用自己的身分。
3. **所有人出題**：每位玩家各出 10 題、總配分 100 分，可在鎖定前編輯及預覽。
4. **主持人鎖定題庫**：鎖定後進入作答階段；未交卷前可依規則解鎖。
5. **各玩家作答**：只看到其他出題者的題目，完成所有必答題後交卷。
6. **主持人公布答案**：依目前版本的流程，所有人交卷後公布。
7. **原出題者人工批改簡答題**：其餘可自動評分的題型由系統計分。
8. **查看作答紀錄與排行榜**：可依玩家或出題者檢視回答，並切換各出題者榜單。

**範例：** A、B、C 各出 10 題（每人題庫 100 分），A 只回答 B、C 的 20 題，因此 A 的最高分是 **200 分**，不是整間房的 300 分。同理 B、C 也各是 200 分滿分。

## 出題方式

支援四種題型，**沒有獨立的「圖片題」題型**：

| 題型 | 出題方式 | 評分 |
| --- | --- | --- |
| 選擇題 | 固定四個選項，使用 Radio 指定唯一正確答案；各選項可附圖 | 自動 |
| 是非題 | 出題者直接選擇「是」或「否」 | 自動 |
| 填空題 | 設定標準文字答案；支援用 `\|` 分隔多個可接受的答案 | 自動比對 |
| 簡答題 | 設定參考答案，讓其他玩家自由作答 | 原出題者人工評分 |

### 圖片與題目預覽

- **題幹**：可用只有文字、只有圖片，或文字搭配圖片。
- **選擇題選項**：A、B、C、D 每項皆可用只有文字、只有圖片，或兩者並用。
- 完全沒有文字及圖片的題幹／選項，不應允許儲存。
- 題幹附圖位於「題目內容」區塊；可使用**預覽題目**檢查玩家看到的畫面。
- 重新編輯既有題目時，應顯示已儲存的題幹圖與選項圖；沒有更換圖片時保留原路徑。
- 切換選擇、是非、填空、簡答題型時，應以**目前選取題型**的答案欄位為準；像 `__FQ_IMAGE_ONLY_0__` 這種內部圖片選項識別碼不得顯示或寫入填空、簡答答案。
- 純圖片選項仍能選為選擇題的正確答案；圖片本身不是由 AI 進行辨識。

### 配分規則

- 每題預設 **10 分**，每位玩家最多 **10 題**，完整題庫總分 **100 分**。
- 第 10 題自動補足剩餘分數；單題至少 1 分。
- 前面題目不能把剩餘分數用完，導致後面題目只能配 0 分。
- 例如前 8 題共 90 分，第 9 題若配 10 分會被拒絕（第 10 題只剩 0 分）；配 9 分則第 10 題可補 1 分。
- 在鎖定前請檢查每題、總分與正確答案。

## 作答與交卷

- 玩家**不會作答自己的題目**；畫面與資料庫的交卷驗證均應依此規則計算必答題。
- 交卷需完整回答所有其他玩家的題目；不接受漏答、無效題目 ID、自己題目的答案或重複交卷。
- 作答中若重新整理，分頁登入狀態會嘗試恢復；**不代表未交卷的文字草稿一定會保存**，請以實際畫面及資料庫狀態為準。
- 題幹與選項圖片應於作答時正常顯示；如看不到圖片，應檢查 Storage 檔案、圖片網址與資料庫回傳欄位。

## 閱卷與人工評分

### 人工評分

- **誰出的簡答題，就由誰批改**；不由主持人統一代評所有人的簡答題。
- 閱卷時會顯示**實際作答者的暱稱**，目前**不是匿名評分**。
- 出題者**不會評自己的答案**，因為玩家本來就不應回答自己出的題目。
- 分數不可低於 0 分或高於該題滿分；尚未人工評分的簡答題需保留待評提示。

### 公布答案後的作答檢視

閱卷／作答紀錄提供兩種切換方式：

1. **依作答者**：選擇 A、B 或 C，查看該玩家回答其他人題目的答案；也可查看**自己的作答內容**。不把自己的出題當作自己的作答。
2. **依出題者**：選擇 A、B 或 C，查看這個人出的題目，以及**其他玩家分別回答了什麼**。

這兩種方式都是**瀏覽作答成果**；人工評分的寫入權限仍限於各題的原出題者。

## 排行榜

- **總排行榜**：每位玩家的得分與可得滿分，均只計入**其他人出的題目**。
- **依出題者切換**：選擇「A 出的題目」，只比較 B、C 等其他玩家對 A 題庫的得分；**A 自己不列在 A 的題庫榜單中**。
- 能比較「誰的總分最高」，也能看「**誰最了解某一位出題者**」。
- 若簡答題尚未人工評分，應顯示待評分狀態，勿將未完成的評分誤解為最終成績。

| 玩家數 | 假設每人出滿 100 分 | 每人最高可得分數 |
| ---: | --- | ---: |
| 2 | 只回答另外 1 人 | 100 |
| 3 | 回答另外 2 人 | 200 |
| 4 | 回答另外 3 人 | 300 |
| 5 | 回答另外 4 人 | 400 |

> 上表假設所有玩家都完成 10 題且各自題庫總分為 100。若未完成出題，應以實際可回答題目的總配分為準。

## 房間管理與分頁狀態

### 主持人

- **剔除成員**：可於大廳／題庫尚未鎖定階段剔除非主持人成員；既有實作可能連帶移除該成員的題目，操作前請確認。
- **鎖定**：所有人完成題庫後鎖定，進入作答。
- **解鎖**：僅限房間已鎖定、**尚無任何玩家交卷**且未公布答案的情況；有人交卷或答案已公布就不可解鎖，避免出題內容在作答後被變更。
- **公布答案**：待所有玩家交卷後開放結果檢視與後續人工評分。

### 同一瀏覽器開多個測試玩家

- 使用 `sessionStorage` 保存目前**分頁**的房間、玩家與畫面狀態，重新整理後嘗試恢復。
- **主動離開房間**才清除該分頁儲存的工作階段。
- 同一瀏覽器可開多個**新空白分頁**各自登入不同玩家。
- 避免使用瀏覽器的「複製分頁」，因為部分瀏覽器會複製初始 `sessionStorage` 狀態。
- 關閉分頁或瀏覽器後能否自動恢復，依瀏覽器行為而定；必要時以原暱稱及 PIN 重新加入。

## 技術架構與部署

- **前端**：HTML、CSS、原生 JavaScript。
- **後端**：Supabase PostgreSQL（主要透過 RPC 存取）、Supabase Storage（圖片）。
- **部署**：GitHub Pages 靜態網站。
- **前端設定**：在 `config.js` 設定 `SUPABASE_URL` 與 `SUPABASE_ANON_KEY`（或目前專案使用的公開 publishable key）。**不要把 `service_role`／secret key 放進前端或 GitHub。**
- **本機測試**：使用 Live Server 或其他 HTTP 靜態伺服器，不建議直接透過 `file://` 開啟 `index.html`。

### GitHub Pages

1. 將完整前端檔案推送至 GitHub repository（包含 `index.html`、`style.css`、`app.js`、`config.js`）。
2. 在 GitHub → Settings → Pages 選擇從 `main` 分支 `/root` 發布（若使用不同部署設定請依專案現況調整）。
3. 部署完成後以 HTTPS 網址進入遊戲。
4. 更新版本後強制重新整理，避免 `index.html` 與 `app.js` 版本不同造成找不到按鈕或 JavaScript 初始化錯誤。
5. 先使用新測試房間驗證，再交給朋友正式遊玩。

## Supabase 更新方式

**既有正常運作的資料庫請勿重新執行 `supabase/schema.sql` 來升級，也不要刪除或重建資料表。**

1. **備份** Supabase 資料與目前 Storage 設定。
2. 核對目前已套用的升級檔；在既有版本上按缺漏套用增量 SQL。**不要在不明版本的資料庫上盲目全部重跑。**
3. 以目前最新功能而言，排行榜涉及 `supabase/upgrade_v4_5_5.sql`；先前版本另有圖片、出題、解鎖、交卷及閱卷相關升級。
4. SQL 成功執行後，部署相容的前端版本，重新整理頁面並建立新測試房間。
5. 透過 Supabase SQL Editor 與瀏覽器 Console / Network 調查實際錯誤。

本專案包含的歷次升級檔（按版本順序）：

supabase/upgrade_v2.sql
supabase/upgrade_v3.sql

supabase/upgrade_v4_1.sql
supabase/upgrade_v4_2.sql

> **注意：** 部分版本只修改前端，沒有 SQL 檔。這些歷史 SQL 是循序修補的紀錄，**尚未驗證可從全新 Supabase 專案一次連續執行到最新版**。請勿把這份清單當作已驗證的全新安裝程序。

### 圖片資料結構與診斷

- 題幹圖片：`quiz_questions.image_path`
- 選項圖片：`quiz_questions.option_image_paths`（JSON 陣列，對應四個選項）
- 圖片檔案：Supabase Storage 的 `quiz-images` bucket。
- `my_questions()` 需回傳 `option_image_paths`，供出題者**重新編輯**時還原既有圖片。
- `list_questions()` 也需回傳可用的圖片路徑，供**作答畫面**顯示。
- 若「有上傳但編輯時圖片消失」，應先檢查表格欄位與 `my_questions()` 回傳，再檢查公開 URL；**不要直接刪除資料或要求重傳圖片**。
- 相關診斷檔：`supabase/diagnose_option_images.sql`。

## 測試清單

### 房間及題庫

- [ ] A 建立房間，B、C 分別從新分頁加入；重新整理後維持各自分頁身分。
- [ ] 每人分別出 3 題選擇、2 題是非、2 題填空、3 題簡答，共 10 題／100 分。
- [ ] 選擇題四個 Radio 可指定標準答案；是非題直接選是／否。
- [ ] 第十題自動補分；測試配分超額或讓末題為 0 時被拒絕。
- [ ] 題幹可純圖片；選項可純圖片；預覽、儲存、重新編輯後圖片仍存在。
- [ ] 反覆切換題型，不出現圖片內部識別碼或錯誤答案。
- [ ] 主持人可在大廳剔除成員；鎖定後不再提供不安全的剔除流程。
- [ ] 鎖定後、尚未交卷前可解鎖；已有交卷或已公布答案時不可解鎖。

### 作答、閱卷及成績

- [ ] A 只看到 B、C 的 20 題，B、C 同理；不看到自己的題目。
- [ ] 題幹及四個選項圖片在作答時正常載入。
- [ ] 每人完整回答對方題目後可交卷；漏答與重複交卷被拒絕。
- [ ] 公布答案前不會意外揭露標準答案。
- [ ] 原出題者能看到其他作答者暱稱並批改自己的簡答題，不會批改自己。
- [ ] 依作答者可看到自己的提交答案；依出題者可查看其他玩家如何回答該人的題目。
- [ ] 三人各出 100 分時，**每人總榜滿分 200**。
- [ ] 選擇 A 的題庫榜，僅列 B、C，各自滿分 100；其他出題者亦同。
- [ ] 簡答尚未批改時明確顯示待評分，不把未完成分數當作結算結果。

## 安全與已知限制

1. **簡化登入，不適合正式高風險場景。** 房間代碼＋暱稱＋PIN 與瀏覽器 player ID 無法提供強身分保證；若要正式公開使用，建議導入 Supabase Auth 或 Edge Function 簽名工作階段、登入限速與後端權限加固。
2. **圖片目前採公開讀取的原型設定。** 具備 URL 的人可能存取圖片；匿名上傳機制也不適合存放個資、私人照片或敏感資訊。公開版建議改為 private bucket 與簽名 URL。
3. **Storage 孤兒檔案。** 若圖片上傳成功但題目儲存失敗，可能留下未被題目引用的圖片；目前仍需額外清理機制。
4. **分頁狀態不等於雲端草稿。** 不保證未送出的題目或作答內容在所有瀏覽器情況下完全復原。
5. **成績仍需實機驗收。** 專案版本整合經過多次修正；升級後請使用多帳號測試交卷、閱卷、人工評分與排行榜，不能只依語法檢查宣稱所有功能均通過。
